# Data

Sources of data for a design: a file, a link or a sheet whose rows later fill the design's layers. This folder holds the source record; bindings and iterators build on it.

- **Tier:** core
- **Requires:** core, pages, frame; uses: text, image, auto-layout
- **Contributes:** kinds `DataSourceKind`; the service `DESIGN_DATA_SOURCES` (`engine.service(...)`); source types `file` and `http`; formats `csv` and `json` (also NDJSON); designCanvas: `afterEdit` (`syncData`), `onRemove`; text: `textTemplates` (`BOUND_TEXT_TEMPLATE`); designEditor: `leftTabs` (the Data tab, order 25, after Assets; kept in the Catalog mode), `propertySections` (`data.bindings`, the Data section, order 85: after Effects, before Export; one layer selected; not kept in the Catalog mode's sidebar), `data.repeat` (the Repeat section, order 33, right after the frame's auto layout; one layer selected that is a frame or sits in one, `repeatTargets`) and `data.copy` (an iterator's copies, order 1), `layerBadges` (`data.copy`), `sessionHooks` (`data.services`)
- **Points it owns:** `dataSourceTypes` (where data comes from; built-ins and plugins), `dataFormats` (how raw data becomes rows), `dataScopeProviders` (`DataScopeProvider`, `(doc, frame, root) => ScopeLayer[] | null`, `root` the sources' scope the asker built: the loops another module puts around a top-level frame, such as a brochure's page and section repeats), `dataLocaleProviders` (`DataLocaleProvider`, `(doc, node) => string | null`: the language data is written in inside a top-level layer, asked of that layer; the first answer wins, none the app's), `dataPreviewSetters` (`DataPreviewSetter`, `(doc, layer, nodeId) => DataLoopPreview | null`: for a loop another module puts around a layer (`layer.owner` its section or page), where it comes from (`from`, "Section Product"; left out for a card repeater's loop, which data names) and its preview row's stepper as seen from that layer (`DataPreviewStep { count, row, set(row) }`, `set` one undo step that may throw; `null` where the row is fixed); the first answer wins, for In scope), `dataSourceForms` (UI, `ui/data.points.ts`: a source type's own settings form, `{ type, component }` with `SourceFormProps`, keyed by the type's id). A source type's `icon` is a lucide icon name (a string), since engine code cannot import the UI icon type.

## How it works

- **The record** (`source/`): a `data-source` element (`DataSourceKind`) is a record, not a layer: never drawn or hit, `creatable = false`, `boxed = false`. It has a `name`, a `sourceType` (where the data comes from) with its `settings`, a `format` (`"auto"` or a format id) with `formatOptions`, `rowsPath` (where the rows are in the data, such as `products` or `data.items`, `""` the data itself; `null`, the default, the first list found), the `fields` found in the data (`DataField`: `path`, `alias`, `type`, `format`, `hidden`), the last copy `snapshot` (`DataSnapshot`: an asset id, `updatedAt`, `rowCount`, `hash`, and from this version `lists`, the lists of objects the data had that could be its rows (`findLists`: outermost first, lists inside a list's items left out, at most 20), and `extras`, the plain values at the top of the data (`extraValues`: `total: 194`, at most 8, long texts cut); `null` until the data is fetched) and `images`, assets the data names. `assets(el)` lists the snapshot's asset and every image, so they stay in the file and copy with it; `fillDefaults` fills every field for older records.
- **No errors on the record**: a failed fetch is device-local and is kept in memory by a service, never written to the file.
- `createDataSource(index, { name, sourceType, settings, format?, formatOptions? })` makes one; `isDataSource(el)` narrows.
- **The snapshot** (`update/snapshot.ts`): the parsed rows are saved as a document asset, `{ version: 1, rows }` as UTF-8 JSON, with a SHA-256 `hash` of those bytes. Assets are outside the undo history and never deleted, so undoing an Update just points the record back at the previous asset (and its fields). `readSnapshot` parses each asset once (cached per Yjs doc, then by asset id: an asset never changes); the cached rows are frozen (the array and each row) and typed `readonly`, since every reader shares them; no snapshot yet reads as no rows, while a missing asset (not on this device yet, as in a live session before it arrives; not cached, so it reads once it arrives) or a broken one reads as `null` (`DESIGN_DATA_SOURCES.rows` gives no rows for it).
- **Update** (`updateSource`): loads the source's secrets from the device (none when they are bound to another origin, see Secrets), checks the required settings (`Missing: <keys>`), finds the chosen files' paths on this device (`requireFilePaths`: "Pick the file again on this device." without one, and a refusal for a path inside the app's data folder, `services.isPrivatePath`), runs the source type's `update` (`fetching`), fails with "The source answered a web page, not data." when the result is HTML (`isWebPage`: a `text/html` mime, or text starting with `<!doctype html` or `<html`), picks the format (`record.format`, or `detectFormat` for `"auto"`) and parses (`parsing`) — these steps are `readData`, shared with Try it — turns the result into rows (`normalizeRows(parsed, rowsPath)`: with a path, the list there, failing with `No list at: <path>` (`UPDATE_ERRORS.noList`) when nothing there is a list), guesses the fields keeping the known ones (`guessFields`), saves the pictures the data names (`images`, see Images), and saves (`saving`): the new assets are added first, then **one** `checkpoint` and one `update` of `snapshot` (with the data's `lists` and `extras`, written on every Update), `fields` and `images` (only the ones that changed). When the hash matches the last snapshot no asset is added and only `updatedAt` changes (`changed: false`), unless this device lacks the old asset: then the new one is added and pointed at. Any failure writes nothing: the result is `ok: false` with the message and the previous snapshot stays.
- **Try it** (`previewSource`, the service's `preview(input, signal)`): runs settings a form holds, not saved, once as Update would (`readData`, `normalizeRows` with the `rowsPath` given, `guessFields` over the known `fields`) and gives the first 50 rows, the row count, the fields, `lists` and `extras`, or `ok: false` with the message (`aborted` when cancelled). It writes nothing: not the record, not a secret, not a picture. Secrets typed in the form are used for this one request; the ones this device keeps for `sourceId` only through `loadSourceSecrets`, so only while the settings' origin is the one they were entered for; a path typed now (absolute) is used, else the one kept for the source, with the same private-folder refusal.
- **The service** (`DESIGN_DATA_SOURCES`, `DesignDataSources`): the only place that makes, edits and updates sources, one undo step each (`checkpoint` first). The editor hands it the registered types and formats and the platform's `DataServices` with `setContext` (`null` when it closes); `create`, `setSettings`, `missingSecrets` and `update` throw "Data sources aren't ready: no editor is open." without one. `error(id)` is the last failed Update's message and `stage(id)` the running one's step, both in memory only (device state: another machine may have the key). `types()` and `formats()` give the registered ones (empty without a context). The context and the Update state are shared by every service on the same Yjs doc (`SharedState`), because an agent's workspace has its own service on a proxy of the document and must reach the editor's platform and see the Updates the tab runs. `onChange` fires on record changes and on Update stages. One Update of a source runs at a time: a second `update` call while one runs shares the first run's result; `updateAll` runs them one after another. A cancelled Update (its signal aborted) returns `ok: false, aborted: true` and is not recorded in `error(id)`. Removing a source forgets its error and stage, and an Update still running for it records nothing.
- **Secrets**: `create` and `setSettings` take the raw form values and split them with the type's specs (`splitSecrets`): the file keeps only the safe settings (a secret pair keeps its names, values `""`), the device's `SecretStore` keeps the rest under `data-source:<sourceId>:<key>` (`key` for a secret setting, `key.name` for a secret pair's value). An empty (`""`) or left-out value keeps the stored one, since a form round-trip carries `""` for every secret it can't show; a secret setting given `null` is deleted, and a pair name that is gone has its value deleted; `remove` deletes every secret of the source. An empty stored value counts as missing: `missingSecrets(id)` lists the required secrets (`required`, or `requiredWhen: { key, value }` while that setting has that value, `secretRequired`: a link's token only while its sign-in is `bearer`) and secret pair values this device doesn't have, and Update checks the same (`missingSecretKeys`, with `missingSettings`) before fetching, failing with `Missing: …` instead of sending an empty header. Undo never brings secrets back: they live on the device, outside the document.
- **Origins** (`DataSourceType.secretOrigin`, the link's URL origin): whenever secret values are written, the origin they were typed for is stored as `data-source:<id>:@origin`. `loadSourceSecrets` (Update, `missingSecrets`, the tab) gives none of them when the settings' origin isn't that one (or none is stored), so they read as missing (`Missing: …`, "Needs a key on this device") and are never sent elsewhere. Typing secrets again re-binds the origin to the current URL; when that moves, the stored secrets not typed again are deleted, so an old header never follows the link.
- **File paths**: a path is this device's, never the file's. A `file` (or `folder`, such as the file source's `imagesFolder`) setting given an absolute path keeps it as `data-source:<id>:@<key>` (`@path`) and only its base name in the settings; another name (or none) deletes the stored path. Only a path supplied in this call is saved: an absolute value equal to the record's (echoed from the document, or a legacy record) is reduced to its name, its stored path deleted, and never trusted. Update reads the device path (`ctx.files`); with none it fails with "Pick the file again on this device." and the file setting shows that line under the name (a folder without one doesn't fail the Update: its image files fail one by one, and the setting says "Pick the folder again on this device."). Paths inside the app data folder (where `secrets.json` is) are refused, by Update and by `platformDataServices.readFile` itself. `missingFiles(id)` lists the file and folder settings without a path here. A folder inside the app data folder fails the Update ("This folder is in the app's own data folder…"). `remove` and `forgetRemovedSources` delete every device key of a source (`deviceKeys`: secrets, `@origin`, file paths).
- **Names** (`sourceName`): a source's name is what bindings use, so it is a lower-case identifier (`[a-z_][a-z0-9_]*`; accents dropped, other characters become `_`, a leading digit gets `data_`), never one of `RESERVED_NAMES` (`page`, `pages`, `title`, `section`, `date`, `toc`, `item`: the brochure's own placeholders) nor an iterator's row name (`iteratorNames`: it would hide the source inside that iterator), and unique (`_2`, `_3`…). A new source is named from `type.defaultName(settings)` unless given a name; `rename` goes through the same rule.

## Links

- **Settings** (`httpSettings()`): `url` (required), `method` (`GET`, `POST`), `auth` (`none`, `apikey`, `bearer`, `basic`) with `apiKeyName` (default `X-API-Key`), `apiKeyIn` (`header` or `query`) and the secrets `apiKey`, `token` and `password` (each `requiredWhen` its sign-in) and the plain `username`; `plainHeaders` (pairs kept in the file) and `headers` (pairs whose values stay on this device, `headers.<name>`); `bodyKind` (`none`, `form`, `json`, `text`) with `form` (plain pairs) and `body` (text).
- **The request** (`buildHttpRequest(settings, secrets)`, pure): the plain headers, then the private ones (their values from `secrets["headers.<name>"]`); the sign-in replaces a header of the same name, whatever its case (an API key in its header, or set in the link's query with `apiKeyIn: "query"`; `Authorization: Bearer <token>`; `Authorization: Basic` with `username:password` in UTF-8 base64). A POST sends its body by kind (a form URL-encoded) with a `Content-Type` unless a header sets one. A record from before body kinds (no `bodyKind`) with a body sends it as written, with no `Content-Type`, as it always did (`httpBodyKind` reads it as `"raw"`).

## Images

- **Saving the data's pictures** (`downloadImages(rows, fields, known, { doc, services, folder, signal, onProgress })`, run by Update between parsing and saving, stage `images`): every value of an `image-url`, `image-base64` or `image-file` field, once per `imageKey`, not already in the record's `images` with an asset this device has, is fetched: a link (`http(s)` only) with `services.http.getBytes`, never with the source's secrets; a `data:` URL (base64 or percent-encoded) or bare base64 decoded (`decodeImageData`); a file name read with `services.readFile` inside the chosen folder only (`imagePathIn`: an absolute name, a drive or a `..` step is refused; subfolders are joined with the folder's separator; each resolved path is checked with `isPrivatePath` too). 4 run at a time, and `onProgress(done, total)` reports them. Bytes are kept only when their first bytes are a picture (`isImageBytes`: PNG, JPEG, GIF, WebP, or an SVG by the renderer's own `isSvg` from `@canvas`, so a saved picture always decodes) of at most `MAX_IMAGE_BYTES` (25 MB, checked after reading; base64 far over it isn't decoded); anything else, a failed download or a missing file is in `failed` with its reason (`ImageFailure`: `unreadable`, `notImage`, `tooLarge`, `overLimit`), never throws and never paints an empty fill (the binding keeps the current picture). At most `MAX_NEW_IMAGES` (2,000) new pictures per Update; the rest are failed too (`overLimit`), and the next Update takes the next ones. A cancel stops the downloads and adds nothing: the assets are added (`createId()`) after every picture is in, and nothing awaits between that and the record's update, which writes the merged `images` with the snapshot in one undo step.
- **Device state**: `UpdateResult.imagesFailed` (and `imagesOverLimit`) count them; `imagesTooLarge` the ones over 25 MB; the service keeps the last good Update's in memory (`imageFailures(id)` the values, `imageFailureDetails(id)` with reasons, `imagesOverLimit(id)`) and the running one's `progress(id)`. The folder (`imagesFolder` on the file source, the first `folder` setting of a type) is device-local like a file path (`@imagesFolder`).

## Bindings

- **Planning a layer** (`planBindings(el, scope, { kinds, locale, images })`, pure): its text from `dataText` (`resolveDataText`: `resolveRichTemplate`, each token written with `formatValue` in `locale`; a token reading nothing, no such name or an `undefined` value (`readValue`), writes nothing and is listed in `missing`), laid out again with `alignedTextPatch` (the text module's: an auto-width text keeps its aligned edge, as the catalog's page items do). Each `dataBindings` entry is written the way its kind writes a variable's value (`bindingWrite`, `writePatch`): the path's `BindableField` in `kinds.kindOf(el).bindable(el)` says the type, the data value becomes that `ResolvedValue` (a number with `toNumber`, a color with `parseTokenColor` (`#rgb`…`#rrggbbaa`), a boolean with `toBoolean`, a string with `formatValue` and the binding's format) and `kind.bindPatch` writes it (an opacity clamped, a size through resize, a text's typography laid out again, a paint's alpha in its opacity), folded over the layer as `syncTokens` does. `fills.<i>.image`/`strokes.<i>.image` are data's own: `images(value, sourceId)` becomes the paint's `assetId`, looked up among the pictures of the source the value comes from (`LookupResult.source`, the source of the expression's first name in the scope that has it: file names are relative to each source's folder, so sources' pictures are never merged) (another paint becomes an image paint keeping its opacity and visibility). A path the kind doesn't offer, a value that doesn't fit, a picture not saved yet (`null`) or a binding reading nothing leaves the field alone. `visible` follows `dataVisible` (`evaluateCondition`); with `dataHideEmpty` a text whose template came out `empty`, or a layer whose image value is empty, is hidden (a filled image doesn't clear an empty text: any empty part hides it); without either, `visible` is the user's. A condition reading nothing (`readValue`: no such name or an `undefined` value) is in `missing` too. **Unreadable sources:** the root scope leaves out a source whose snapshot reads `null` and lists its name in `unreadable` (`DataScope.unreadable`; `DataScope.sources` maps each name to its source id); a template with a token, a binding or a condition whose first name is such a source (`readsUnreadable`, a nearer scope's name shadowing it) is skipped, writing nothing for that part, and listed in `PlannedBindings.unreadable` (`"text"` for the template); "hide when empty" isn't decided while the text or a picture is unreadable, and an unreadable condition leaves `visible` alone. So a peer whose snapshot hasn't arrived never blanks the layers. **Lists:** a list's items are written with commas, or with the field's format `list` (`FieldFormat.list`, `ListShow`) only the first (`"first"`) or how many there are (`"count"`). **Numbers:** a string counts as a number (`toNumber(value, type)`, for number fields, conditions and formats) only for a numeric field (`integer`, `number`, `currency`) or as plain decimal text (`^-?(0|[1-9]\d*)(\.\d+)?$`): "007" and "0x1A" stay text; `Intl` formatters are made once per locale and options (`intl-formats.ts`). Only fields that differ from the layer's are in the patch (`sameValue`: numbers within 1e-3, colors in either case, as variables compare), so the second pass writes nothing.
- **Language:** values are written in each client's app language (`getLocale()`), so two people in a live session may see `1,299.50` and `1.299,50`, unless a `dataLocaleProviders` entry answers for the layer's top-level ancestor (`DataScopes.localeFor`, asked once per top-level layer per sync: a brochure page's language); the sync keeps one `BindingContext` per language.
- **Run styles of a bound text** (`carriedTemplate`, `carryRunEdit` in `bindings/carry-run-edit.ts`): the sync rebuilds a bound text's `runs` from `dataText`, so a style written to the shown `runs` outside the editor (the Typography section on the whole text, the token sync restyling a range's text style, `syncRunStyleBindings` unlinking a `textStyle`, an agent's `update_nodes` runs) would be undone, and the hooks would undo each other until the pass cap. So when an edit's `before` has `runs` (and no source changed), the sync carries the difference into the template first: when the text still reads what the template gives, each piece of the template (a character, `{{`, a token; `ResolvedTemplate.spans`) takes the change (fields set or cleared) its shown text got; a token whose output changed in different ways keeps its style (and the sync shows it again), and a token that came out empty takes the change when the whole text got one change. The template is written in the same edit; its shown runs then equal what it resolves to, so nothing else changes. **Why here, not a run-mapping hook on `TextTemplateSource`:** the writers of `runs` are many and in several modules (the text kind's `bindPatch` for range styles, `syncRunStyleBindings`, the Typography section, `update_nodes`, the Scale tool); one check in the sync that owns templates catches all of them, including future ones, without each writer knowing templates. `style_text_range` refuses a range that isn't the whole text on a text a template claims ("style a bound text's ranges while editing its template"), since a range of the shown text can cut a token. **The passes** (hooks run in module order: variables' `syncTokens`, then `syncData`, then the text module's `syncRunStyleBindings`; a hook's writes are the next pass's change): Typography on a bound text: pass 1 `syncData` sees `runs` in `before`, writes only `dataText` (the shown runs already match it), `syncRunStyleBindings` follows the shown runs; pass 2 (`before`: `dataText`, maybe `bindings`) every hook finds nothing to write. A text style changed: pass 1 `syncTokens` restyles the shown runs; pass 2 `syncData` carries them into `dataText`, `syncTokens` sees its value held; pass 3 nothing. A range's style unlinked by `syncRunStyleBindings` (pass 1): pass 2 `syncData` carries the cleared `textStyle`; pass 3 nothing.
- **Editing a bound text** (`BOUND_TEXT_TEMPLATE` in `bindings/bound-text-template.ts`, contributed to the text module's `textTemplates`): a text with `dataText` (and no `catalogText`, which the catalog fills) opens in the editor on its template, shows what's typed while editing, and its commit writes only `dataText`; the sync then writes the resolved text. Writing only `dataText` unlinks nothing (no binding's path nor `visible` is in the edit's `before`).
- **Hand edits unlink**, as variables do (`droppedBindings`, `droppedVisibility` in `sync/hand-edits.ts`): a bound field the edit wrote (its root in the edit's `before`) with anything but what its data gives (`writtenFields`, the kind's `bindValues`) loses its binding and keeps what was written; the sync's own writes hold the data's value, so they never unlink. Writing `visible` by hand (the eye) on a layer the data would set back drops `dataVisible` (to `null`) and `dataHideEmpty` (to `false`), and the choice stays. One field has one binding from both sides: a variable bound in the edit (`before` has `bindings`, a path new or naming another variable) over a `dataBindings` key (`pathsOverlap`, a picture's key by its paint) drops that data binding, and one at `text` drops `dataText` (`replacedByVariables`), before anything is planned, also beside a source change. An edit that also changed a source (`affectedData`'s `all`) unlinks nothing: the sync owns it.
- **Syncing on request** (`syncDataFor(doc, nodeIds, kinds)`, `sync/sync-data.ts`): fills the layers under those nodes (each root and what it holds) and brings the iterators among them in step, in the current transaction, through the same fill as the sync with no hand edits to read: for a module that changed what is around a page (catalog's page repeats) without editing its layers.
- **The sync** (`syncData(doc, change, kinds)`, the module's `designCanvas.afterEdit`, so inside each edit's undo step): `affectedData` says what to fill. `all` when a source record was added or removed, or its `name`, `fields`, `images` or data changed, compared from the edit's `before` (the changed fields' earlier values) against the record now: an Update that found the same data moves only `snapshot.updatedAt` (and writes equal fields again), and a settings change needs an Update to matter, so neither refills anything. Otherwise the changed layers that carry data fields. It builds the root scope once per run (`dataSourcesIn` and `readSnapshot`, the same rows `DESIGN_DATA_SOURCES.rows` gives; the rows are frozen and never written), keeps each source's `images` in its own lookup by `imageKey` (a URL or file name as it is, base64 as `"b64:"` + a 64-bit FNV-1a hash of the whole text + `:` + its length; keys saved by older files don't match and are downloaded again), leaving out pictures this device lacks the asset of, so their layers keep the current picture, drops data bindings a variable replaced, unlinks hand edits, carries run styles into templates (below), plans each layer (with `all`, one pass over the document) in its language (`localeFor`, else the app's `getLocale()`), and writes the patches with one `updateMany`; then it brings the iterators the edit reached in step (see Repeat, Writing copies). Its writes run it again with the layers it changed, whose plans now differ in nothing, so it ends. Layers with a catalog template (`catalogText`) are skipped: the catalog fills them.
- **Binding a layer** (`bindData(doc, id, patch, scope, kinds?)`, `bindings/bind-data.ts`): the one edit the Data section and agents share. `patch` (`BindDataPatch`) may set `text` (a text's template; `null` stops it and the text keeps what it shows), `bindings` (by field path; `null` unbinds one, keeping its value), `visible` (the show condition, `null` removes it) and `hideWhenEmpty`; what's left out stays. Everything is checked before writing, with English errors naming the bad path: the layer exists and is a design node, a template only on a text and each of its tokens a data path (`parseTokens`, `parsePath`), each binding key a field path and its `path` an expression starting with a name, an image key's paint present, a binding's `format` checked as a field's is (`readFieldFormat`, `source/read-field-format.ts`, shared with `set_data_source`; the currency upper-cased), the template's runs `{ start, end, style }` sorted, apart and inside its text, no template on a text with a catalog template (`isCatalogText`, the one check `syncData`, `BOUND_TEXT_TEMPLATE` and the section use), with `kinds` each key a field the kind offers (`bindable`, not a style, or `dataBindableFields`) and the data's type (`dataTypeOf`: the field's, `integer` for a row count, unknown when the source doesn't list it) one `acceptedTypes` allows for it (the Data section's table: colors `color`, numbers `integer`/`number`/`currency`, pictures the image types, anything for a boolean or a text), a condition's op one of `CONDITION_OPS` and its value a text or a number, and `hideWhenEmpty` a boolean. The checks are in `bind-data-checks.ts`. One field has one binding: binding a field (or a text's template) removes the variable binding of that field (`el.bindings`, any path overlapping it, so a `fills` style goes too; for a picture, the paint's), in the same write. When the edit leaves neither `dataVisible` nor `dataHideEmpty` on a layer that had one, a layer the data hid is shown again. One `checkpoint` and one `update`; the sync (an `afterEdit`) fills the layer in the same undo step.
- **Renaming a source** (`DesignDataSources.rename`, one undo step with `doc.batch`): `renameReferences(doc, from, to)` (`repeat/rename-references.ts`, since it reads iterators; `model/` imports it and `iteratorNames` as `repeat/` leaves) parses and rewrites, never text-replaces, the first name of every `dataText` token (`renameTemplate`: only the changed tokens are rebuilt, with `formatPath`; the runs move with their text, a run touching a token covers the whole renamed one; a stored template that breaks `bindData`'s rules is left as it is, so a rename never stops halfway), `dataBindings[*].path`, `dataVisible.path`, and each iterator's `repeat.source` and row paths (`key`, `filter`, `sort`: `renameRepeatPaths`, on the record as stored), in one `updateMany`. A nearer iterator whose row name is `from` hides it: the layers inside it, and its own row paths, are left alone. It runs in the same transaction as the name change, which `affectedData` reads as a source change (`all`), so the rewrite unlinks nothing.

## Repeat

- **The record** (`repeat/`): a frame may carry `repeat: RepeatSettings` (`source`, `as` default `item`, `key`, `filter`, `sort`, `limit`, `designLimit`, `previewRow`, `detached`, `template`: the id of the child repeated, set with the repeat), and a copy of its template child carries `dataCopy: DataCopyTag` (`iterator`, `key`, `source`: the template child's id). `repeatOf(el)` (frames only) and `dataCopyTag(el)` read them defensively: anything malformed gives `null`.
- **Rows** (`repeatRows(repeat, scope, phase)`): the list is `lookup(scope, repeat.source)`, copied (snapshot rows are frozen), then filtered (`evaluateCondition` in a scope with `as` = the row, so paths read `item.price`), sorted, capped by `limit`, and in the `"design"` phase by `designLimit`, `DEFAULT_DESIGN_LIMIT` (24, `repeat/design-limit.ts`) while it's unset, so a long list, or one an Update grows, never floods the document (an export reads `"export"` and makes every row); `total` counts the rows before `designLimit`. Sort and `key` paths are read in the same row scope. Sorting is stable: two values compare as numbers when both are numeric by `toNumber` (a numeric field, or plain decimal text), else as text with `localeCompare` in the app locale and `{ numeric: true }`; empty values go last in either direction. A row's key is its `key` value as text, else its position in the list before filtering and sorting (so changing a filter or sort keeps the other rows' keys; set `key` whenever the list is filtered, sorted or can be reordered); a repeated key becomes `key#2`, `key#3`, numbered in list order. Keys are made over every row shown before `limit` and `designLimit` cut it, so a row has the same key in the document and in an export.
- **Planning copies** (`planDataCopies(frame, template, templateTree, existing, rows, detached)`, pure): one copy of the template per row given (the caller leaves out the row the template itself shows), matched to the copy there by row key (the first by order wins, ties broken by id (`byIndex`) so every device keeps the same one, later ones of the same key go), and each copy layer to its template layer by its tag's `source`. Copies an iterator inside the template made (its frame in the template's tree), and catalog master copies, aren't copied: a nested iterator (its `repeat` copied with its frame) makes its own in each copy. A template that is itself in an outer copy (a nested card's copy, tagged by the outer iterator) keeps its layers (`templateParts`). A kept copy is patched (`copyPatch`, compared as JSON, so a sync that changes nothing writes nothing) except in what its data writes (`dataResolvedPaths`: its `dataBindings` keys, a picture's whole paint, what the kind's `bindPatch` derives such as a bound size's sizing or a bound text's laid-out size, `text`/`runs` from `dataText`, `visible` from a show rule) and what its auto layout decides (`layoutPlacedPaths`: position and filled sides in a layout parent, hugged sides of its own layout). A field holding such a leaf (`fills` for `fills.0.color`) is written with the copy's leaf kept (`mirroredField`), so the patch never looks like a hand edit and never unlinks a binding. Fields a copy never takes: `id`, `type`, `index`, `parentId`, `pageId`, `locked` (always `true`), `x`/`y`, `dataCopy`, `catalogCopy`; a copy's root keeps its place (auto layout moves it), each other layer sits where its template layer does relative to its own parent (that parent's copy where it is now, kept or being added, so a group auto layout moved inside a copy keeps its layers), and in its sibling order. New copies and the parts the template gained come in `add` (`copyNode`: fresh `createId()` ids, locked, tagged; a catalog master's `catalogCopy` and a brochure page copy's `repeatCopy` aren't copied); copies of a key gone, repeats, and parts the template lost are in `remove` with what they hold; copies follow row order right after the template (`orderKeys`: the longest run already in order keeps its indexes, the others get `nKeysBetween` keys). A detached key is left alone. A field the template no longer has stays on its copies (an update can't delete one). Catalog's generated brochure pages copy their template pages with the same pieces, exported for it: `templateCopyParts` (`templateParts`, named apart from catalog's own in the design's barrel), `mirroredField`, `dataResolvedPaths` and `layoutPlacedPaths`.
- **Scope** (`rowScope(parent, repeat, row, index, total)`; `layerScope` is the same for a `ScopeLayer`): names `as`, `$index`, `$number` (index + 1) and `$count` (total). The row name carries the list's source (so pictures resolve per source) and the list's fields re-keyed under `as` (`products[].price` → `item.price`), so formats and types apply inside copies. `rowNames(parent, repeat)` is that row name's fields and source, made once per iterator. A `ScopeLayer` (`repeat/scope-layer.types.ts`: `name`, `value`, `owner`, `label`, `index`, `count`, optional `names` (what the name carries) and `unreadable`) is one loop around a layer as a list of them describes it, outermost first; catalog's brochure repeats yield them for their pages.
- **Loops around a page** (`dataScopeProviders`): a top-level frame (no parent) reads the loops another module puts around it, outermost first: each provider is asked once per frame per `dataScopes` (kept through `invalidate`), their layers joined in contribution order and layered over the root scope (`layeredScope(root, layers)`, `repeat/layered-scope.ts`: each layer's `layerScope`, its `name` the row with `$index`, `$number`, `$count`, carrying its `names` (`rowNames`, so formats, types and pictures apply), an `unreadable` layer's names reading as unreadable; catalog's `expandBrochure` builds its pages' scopes with the same helper). Everything inside the frame, its bindings and its card repeaters, reads them. `root` is one object per pass, so a provider whose answer walks the whole document memoizes it on `root` (catalog's expands each brochure once per pass, `WeakMap<DataScope, …>`). The engine side has only the document, so `register` hands the module host to `readAroundFrom` (`repeat/data-around.ts`, read live, replaced when the design's host is composed again); not exported. `scopeLayersAt(doc, id)` (`scope-at.ts`, `DataScopes.layersFor`) lists every loop around a layer, outermost first: the providers' layers, then each card repeater the layer is the template or a copy of (`owner` the frame's id, `label` its name, `value` the copy's row or the template's preview row, `index` its place, `count` the rows shown before `designLimit`, `names` the iterator's), for the In scope view and agents.
- **The data phase** (`dataPhase(doc)`/`setDataPhase`, `model/data-phase.ts`; `DesignDataSources.phase()`/`setPhase`): `"design"` by default, `"export"` on an export's scratch copy (`dataPhase` is exported, for catalog's repeats), kept per Yjs doc in memory (`SharedState.phase`). The sync and `documentScopes` read iterators' rows in it (`dataScopes(doc, root, phase)`), so in an export every row gets its copy; setting it doesn't sync by itself (`syncDataFor` does).
- **A layer's scope** (`dataScopes(doc, root, phase)`, `repeat/data-scopes.ts`; `scopeAt(doc, id)` in `repeat/scope-at.ts` is it with a fresh root, for the Data section, agents and the `scope` `bindData` takes from its caller): from the layer up, each ancestor frame with a repeat adds `rowScope` for the row the layer belongs to: in a copy, its root's `dataCopy.key` looked up in that iterator's rows; in the template (`templateOf`: the child `repeat.template` names, or in a copied iterator the child copied from it (its tag's `source`); `null` when no child answers to the name, never another child; only an older record without `template` goes by the first child that isn't one of the frame's copies, which a detached copy could be taken for), the preview row (`previewRow` when it's within the rows shown, else 0; no rows: the row name reads nothing, so the template is left alone). An iterator whose list reads a source this device can't read (`IteratorRows.unreadable`, `readsUnreadable`) gives every child one scope where its row name, `$index`, `$number` and `$count` are unreadable, so what reads them is left alone and a nested iterator's list (`item.specs`) is unreadable too. `documentScopes(doc)` (`scope-at.ts`) is `dataScopes` over the document's sources, for several questions at once (`get_data_source`'s iterators). Another child of an iterator (a detached copy) reads the frame's scope, with no row. The sync makes one `dataScopes` per run over its one root scope: each iterator's rows (`repeatRows` in the document's `dataPhase`), what its row name carries (`rowNames`), each row's scope and each layer's scope are made once and remembered, the walk reads ids and fields (only an iterator and its children are read whole), and the layer tree (children by sibling order) is read once and again after a write of copies (`invalidate`), never per layer.
- **Writing copies** (`writeDataCopies(doc, plan)`, no checkpoint): the plan's new layers added (parents first, as listed, handed over unchanged: they share arrays with the template), then the kept layers' patches (a reparenting included) and their new order in one `updateMany`, then the removals (which never hold a kept layer). **In the sync** (`syncIterators`): `affectedData` lists the iterators an edit reached: a frame whose `repeat` changed or that came with one, and every frame holding a repeat around a layer that changed, came, went or moved (its old parent's too), found by walking that layer's ancestors; with `all` (a source changed), every iterator. After the edited layers are planned and written, each iterator, outermost first (by depth), unless its list can't be read on this device (then its copies stay as they are, rather than all go, and only its layers are planned, their unreadable fields left alone: a peer whose snapshot hasn't arrived never removes them), takes its rows but the template's own (`preview`), `planDataCopies` against its other children and their layers, and writes the plan; then every layer whose nearest iterator it is, the template's and the copies', is planned in its row's scope and written in one `updateMany`. An iterator inside (the template's, copied with it, `repeat` and all, and each copy's) is brought in step after it, in its own copy's row scope. A frame whose repeat went (an undo, a peer) has its copies removed: no rows; a frame inside an iterator that no longer repeats but still holds its copies (a copied iterator whose template's repeat went) gets its turn too, which removes them; a frame with no template left loses its copies, and when its repeat named a card (`template`) that is no longer one of its layers (moved out of it), its repeat too (not a copied iterator's, which follows its template's). Everything is written in the edit's undo step, so undoing an Update that changed the row count takes the copies it added or removed with it.
- **Setting a repeat** (`setRepeat(doc, frameId, repeat, { addLayout, kinds })`, one undo step, the only writer): the repeat lives on the container frame, next to its auto layout (width, wrap and gap are its), and repeats one of its layers, the card. It merges `repeat` over the stored one (an optional setting given as `undefined` clears it) and writes `template`: the card `repeat.template` gives (one of the frame's own layers, never a copy: refused otherwise), else the card it repeats now, else the frame's first child. Changing the card while it repeats is allowed: the sync removes the old card's copies (their tag's `source` no longer matches) and makes the new card's in the same step, `detached` starts empty unless given (as it does when `source` changes: the new list's keys aren't the old one's), and the old card stays as a plain layer of the frame. `repeatLayer(doc, cardId, repeat?, opts?)` is the shortcut from the card: it finds the card's parent frame ("Put the layer inside a frame first." without one, `REPEAT_ERRORS.noParentFrame`) and calls `setRepeat` on it with `template: cardId`, turning the repeat on (it then needs `source`) or switching it to this card. Defaults: `as` the first free of `item`, `item_2`…, empty `filter`, `sort` and `detached`. Checked first (`check-repeat.ts`, English errors naming the field): a frame with a layer; `source` a list in the frame's scope (`scopeAt`; a source not readable here passes); a new or changed `as` an identifier (letters, digits, `_`; so never `$…`), not a brochure placeholder (`RESERVED_NAMES` but `item`, the default row name), not a source's name, not the row name of an iterator around or inside it (`rowNameProblem`); the key, filter and sort paths, the ops, and `limit`/`designLimit`/`previewRow` whole numbers. A changed `as` renames the repeat's own row paths and, with `renameReferences(doc, old, new, frameId)`, what reads it in the layers under the frame, in the same step. With `addLayout` (and `kinds`), a frame without an auto layout gets one through the auto layout module's `addAutoLayout`, made a wrapping row (`repeat-layout.ts`: fixed width, hugged height), its checkpoints held so it's the same undo step. Fields this version doesn't know stay as stored, and a repeat that comes out the same (with no layout to add) writes nothing. `null` removes the repeat and every copy it made, and the copies its copied iterators made in outer copies (`dataCopy.source` the frame); the outer iterator's sync then takes the `repeat` off those copies.
- **Copied iterators**: an iterator inside a template is copied with it, and each copy takes the template layer's `repeat` (`copiedRepeat`, `copied-repeat.ts`) with `detached` mirrored: the template iterator's detached copies are template content, so they come along in each outer copy as plain layers, and their rows must stay detached there too. Only `template` differs: it names the copy of the inner template. A kept copy is patched only when that differs, so a second sync writes nothing. `setRepeat` refuses a copied iterator (edit the template's repeat instead).
- **Detaching** (`detachDataCopy(doc, copyId)`, the copy's root or a layer in it, one undo step): the row's key joins the iterator's `detached`, and the copy and what it holds are untagged, unlocked and lose their data fields (`dataText`, `dataBindings`, `dataVisible`, `dataHideEmpty`, and a copied iterator's `repeat`), so they keep what they show: a detached copy has no row to read. Refused where `detachBlocker(doc, iteratorId)` (`detach-blocker.ts`) says so, walking up from the iterator: a frame that is itself a copy (`inside-copy`: "Detach the outer copy first", since the outer iterator would write it over), or one that is the card of an iterator around it (`repeated-card`: the inner repeat is template content, mirrored into every outer copy, so a detached row would show the preview row's data in each; detach the outer copy instead). The Detach button asks the same. `detachedRowsGone(doc, frameId)` lists the detached keys no row of the list (every row, as an export counts them) has any more; none while the source can't be read here.
- **Deleting and copying** (`pruneData`, the `onRemove`; `prepareDataCopies`, the `prepareCopies`): deleting a template takes its iterator's copies and its repeat in the same undo step (an older record without `template` keeps the repeat while the frame has another layer, which becomes the template), and deleting an iterator takes the copies that weren't removed with it (copies still tagged after their iterator went, such as a collaborator's change), and what a removed copy holds goes with it (a copied iterator's own copies). Copied together with their iterator frame, copies are left out of the clipboard (the pasted frame's sync makes its own; its `repeat.template` follows the pasted template, and `detached` stays, as the detached copies are plain layers pasted with it; a pasted iterator whose `as` is a source's name in the target document or the row name of an iterator around the paste takes the first free row name, `firstFreeRowName`, and what reads it in the pasted layers follows, `freePastedRowNames` with `renamedReferences`, the read-only side of `renameReferences`); copied without it, they are freed (`freedPatch`: untagged, unlocked, no data fields, as they look, with everything inside them).
- **Orphan sweep** (`sweepOrphans`, first thing in `syncData`): a tagged layer an edit touched that is no longer inside one of its iterator's copies (dragged out of the frame, or into its template or another plain layer of it), whose iterator no longer repeats (a peer removed the repeat while this one's sync made the copy; a copied iterator's copies are left to its sync, which removes them), or whose iterator frame is gone (checked when the edit removed an iterator: a peer's delete, an undo), is freed with every layer it holds rather than deleted, since the user moved it. Its iterator then makes the copy again if the row still needs one.
- **Copies follow their template:** copies get none of the hand-edit rules (`replacedByVariables`, `droppedBindings`, `droppedVisibility`, `carriedTemplate`): the sync wrote them, and the edited-layer pass leaves every tagged layer to its iterator. A copy is locked, so only an agent (`update_nodes`) can edit one by hand; that edit is written over at once (the change reaches its iterator, which patches the copy back to its template and its row), and a deleted copy comes back. Detach a copy to keep it.
- **It ends:** a sync that changes nothing writes nothing (the plan is empty: copies match by JSON, the data-resolved and layout-placed paths are left out; `planBindings` writes only differences). Pass 1 adds and patches copies and fills them; auto layout (its own `afterEdit`) then moves and sizes the copies; pass 2 sees those layers changed, so it plans their iterator again: the copies' roots keep their place and their filled and hugged sides (`layoutPlacedPaths`), each other layer sits where its template layer does relative to its own parent's copy (auto layout moves a layer with what it holds, so a copy root or an inner group it moved keeps its layers' offsets), their data-written fields equal what their row gives, so nothing is written and the passes end.

Otherwise, for a text (not one with a catalog template, `catalogText`: the catalog fills it), "Text from data" (`TextDataBlock`, a `SwitchField`: on starts the template from the text it shows, with its runs; off stops it) and `TextTemplateField` (the template in a text area, line breaks kept, `useCommitField` with `commitOn: "mod-enter"`: blur or Ctrl/⌘+Enter commit, Escape reverts; a commit goes through `editTemplate`, so the style runs follow the typed change; the braces button's `FieldPicker` inserts `{expr}` where the caret was, `onSelect` keeping it, and commits, and its `onCloseAutoFocus` puts the focus back in the text area right after the token instead of on the button). - `FieldPicker` (exported from `ui/index.ts`, with `FieldPickerButton`: the outline button showing the chosen field's label, which the field rows, conditions and the Repeat section use): a dropdown of `pickerNames(scopeAt(doc, node))`, from `namesInScope`, hidden fields left out, grouped under their source, each by its alias (else the expression) with the first row's value; picking hands the expression exactly as `namesInScope` wrote it (quoted keys kept).

- **Copies** (`design-mode/`): `DataCopyBadge` (`layerBadges` `data.copy`) marks a tagged layer in the layers panel with the list it repeats. `DataCopySection` (`data.copy`, any selected layer tagged): "Row N of <list>" (`copyInfo`: the row's place among the rows shown, else "not shown now"), Edit template (`engine.focusElement` on the tag's `source`, the template layer it copies), Select container (the iterator frame) and Detach (`detachCopies`: `detachDataCopy` once per row selected, one undo step), whose tooltip says a copy follows its template and comes back when deleted until it's detached; where `detachBlocker` refuses it, it's disabled with why (`copyInfo.blocked`): "Detach the outer copy first", or that the repeat is inside a repeated card.

## The Data tab (`ui/`)

- **Platform** (`ui/hooks/data-services.ts`): `platformDataServices` is this device's `DataServices` (`@platform`'s `http`, `readLocalFile` (refusing the app data folder), `secretStore`, `isPrivatePath` over `isAppDataPath`, and `pickFile` over `openFile`, which gives the path, and `pickFolder`). `useDataServices`, the module's session hook, hands it with the registered types and formats (`useDataRegistry`, read once from the host's points) to the service with `setContext` in a layout effect, so it is set before any panel's effect, and `null` when the editor closes.
- **Images:** Update's stage line reads "Saving images… 12 of 40" (`stageText` with `progress`); the row and the Fields section show how many pictures the last Update couldn't save (`ImageFailuresLine`, saying when some were past the limit, and why the others failed: `failureReasons`, "2 are over 25 MB · 1 isn't a picture"), and an image field whose pictures aren't saved yet (its type just changed to an image type, say) says "Update to download its images" (`hasUnsavedImages`). The folder setting is a `FileField` that picks a folder (`DataServices.pickFolder`, `@platform`'s `pickFolder`).
- **Hooks:** `useDataSources()` is `list()`, re-rendered on `onChange` (`useDataVersion`). `useUpdateSource(id)` gives `{ run, stage, cancel, cancellable }`: Updates the tab starts (`ui/hooks/run-update.ts`) keep their `AbortController` by service and source, and the Update all loop its own with its running flag (`useUpdatingAll`), so the row, the detail and the header share them, also after leaving the list and coming back (a second Update all while one runs does nothing); a failed Update is `notifyError`ed, a cancelled one isn't. Update all runs the sources one after another and one cancel stops the rest. An Update an agent started shows its stage but can't be cancelled from the tab. `useSourceSecrets(source)` reads which of the source's secrets (origin-checked, `loadSourceSecrets`) and file paths (`@key`) this device holds, and `missingSecretKeys`, whenever its settings change and on every `onChange` of the service (an agent's secret write, an Update).
- **List** (`DataTab`, `SourceList`, `SourceRow`): the type's icon (`SourceIcon` maps a type's lucide icon name, an unknown one gets the database icon), the name, "N rows · updated 3 days ago" (`relativeTime` in the app's language) or the stage while it runs, the last error in the destructive color (`errorText`: the known engine messages, `UPDATE_ERRORS` and a link's `<url> answered <status>.`, are translated, others shown as they are; failure toasts go through `translatedError` too), "Needs a key on this device" when secrets are missing, and Update (a spinner while it runs; a click then cancels). The header has Update all and "+" (`AddSourceMenu`, one item per type).
- **Add** (`SourceDetail` with no source, `CreateSourceForm`): the type's form (its `dataSourceForms` entry, else `SettingsForm` from its `settings`; it gets `onPreview` without a source id, and a change with `{ update: true }`, a form's own "Save and update", creates the source right away) and the format; picking a file proposes the format from its extension (`detectFormat`). "Create and update" creates the source with its format and options (one undo step, `DataSourceInit.formatOptions`), opens its detail and runs Update. A typed key says "Will be saved on this device".
- **Detail** (`SourceDetail` header: back, the name, renamed with a double-click through the layers module's `LayerName`, and Update; `SourceSections`): settings (the form gets `onPreview` (the service's `preview` with the source's id, format and fields), `rowsPath` and `onRowsPathChange`, and a change with `{ update: true }` updates the source once saved; each committed change is `setSettings`, one undo step; secret inputs are empty, say "Saved on this device" when the device has the value and send `""` unless something was typed, × forgets a secret setting), a picked file switches an explicit format to the one its extension says, while "Automatic" stays automatic; the format (`FormatSelect`: "Automatic" or a format, then its options) and **Rows come from** (`RowsFromField`, once an Update found a list: "Automatic (the first list)" or each of the snapshot's `lists` with its item count, a path the data no longer has kept as "not in the data any more"; picking one is `setRowsPath` and an Update; the snapshot's `extras` under it, "Also in the data: total 194 · skip 0"), the fields as a tree (`FieldTreeView` over `fieldTree`: a field's path keys make groups, `dimensions.width` under a `dimensions` row that opens and closes (`FieldGroupRow`, open by default); each field (`FieldLeafRow`) shows its kind as an icon (`FieldTypeIcon`) opening `FieldKindMenu` (the kinds with their icons, for a list how its items show (`format.list`: all, the first, how many), and Rename, which edits the alias inline), its alias or last key, its first row's value as a layer would show it (`formatValue`), and hide; a list of objects (`inner`: the fields of its items, guessed from the rows) opens to list them read only, with a note that a card repeated inside the card fills them; each change one `setFields`), the first 200 rows (`RowsTable`, the visible fields as columns) and Remove source (`RemoveSourceButton`, after a dialog: undo brings the source back, not its secrets). A source that goes away (undo, an agent) brings the list back.
- **A link's form** (`ui/http-form/`, `HttpSourceForm`, contributed to `dataSourceForms` for `http`): `ConnectionCard` shows the link at a glance (GET or POST, the site, the path, a tag per link setting, the sign-in, the header count and the body; a tag opens the dialog on its tab), and a new link (no URL) opens the dialog at once. `ConnectionDialog` (mounted fresh per opening, so it starts from the saved settings) edits a `ConnectionDraft` (`toDraft`/`fromDraft`: plain and private headers as one list with a lock each, a private value this device keeps shown as "Saved on this device" and `""` keeping it; secrets typed are sent as typed, `""` keeps the stored ones): the request in plain words (`connectionSummary`), the link and method (`UrlBar`), and four tabs: **Link settings** (`ParamsTab`: the query as rows, kept in step with the link both ways, `urlParts`/`withParams`), **Sign in** (`AuthTab`: `ChoiceCards` for none, API key, token, username, each showing only its fields, a note that keys stay on the device and go only to the link's host), **Headers** (`HeadersTab`: `HEADER_HINTS` offered while typing a name with what each is for, their usual values offered for the value, names like `Authorization` or `*key*` starting private, quick adds) and **Body** (`BodyTab`: a GET says it sends none, with Use POST; Nothing, Form (rows), JSON built from rows (`JsonRowsEditor`: text, number, yes/no, empty) or written as code (`JsonCodeEditor`: checked as typed, `jsonProblem` naming the line, Tidy up; JSON with nested parts can't go back to rows), or Text). `PairEditor` rows always end in an empty one that becomes a real row when typed in (it keeps its React key, so the focus stays), and suggestions show in the flow under the field (`SuggestList`, `useSuggest`: Up/Down, Enter or Tab picks, Escape hides), never in a popover, so they work inside the dialog. **Try it** (`TryPanel`, `TryResult`) runs the draft with `onPreview` and shows the counts, Rows come from (a pick runs it again), the extras, the top fields with their kind icons and the first rows (`RowsTable`), or the failure in plain words (`failureTitle` from the site's status: not allowed, not found, the site's problem) with the translated message. "Save and update" (refused while the link isn't one or the JSON written doesn't parse) sets the picked rows path and saves with `{ update: true }`.
- **Checks** (`checks/`, `dataIssues(doc, { nodes?, sources?, kinds? })` giving `{ issues, truncated }`): data that doesn't fit, each `DataIssue` a `kind`, a `nodeId` and/or `sourceId` and an English `detail` (parameters of the translated line, never shown alone). Per bound layer, in its own scope (`planBindings`' `missing`, one root scope and one `dataScopes` per call; copies are left to their template): `unresolved-token` (one per source read, a name that is no source's has none) and `text-overflow` (a bound text with `autoResize: "none"` whose laid-out height, with the data in, exceeds its box); per iterator: `too-many-copies` (over `MANY_COPIES`, 500, copies made while designing, a `designLimit` set that high), `copies-stacked` (several copies, no auto layout) and `detached-row-gone` (`detachedRowsGone`); per source, with the service (this device's memory) and not when `nodes` limits the check: `source-error`, `never-updated` (no snapshot) and `image-failed` (the last Update's `imageFailureDetails`, with reasons). Kinds needed for the layer checks. It stops after `MAX_ISSUES` (500, `truncated`). The Data tab runs it while open (`useDataIssues`, again 300 ms after a document or source change): a source's row shows how many issues are tied to it and its detail lists them (`SourceIssues`, translated in `issue-text.ts`, `issues.*`) with Select for the ones on a layer.

# Prototype

Clickable prototypes inside a design: in the Prototype mode a page's top-level frames are screens, layers (and screens themselves) get interactions that link them, and flows say where a prototype starts and which device it plays on. One file can hold an app's flows and a website's side by side.

- **Tier:** feature
- **Requires:** core, pages, frame
- **Contributes:** kinds `PrototypeFlowKind`; designCanvas (`prototype.canvas.ts`): `kinds`, `onRemove` (`prunePrototype`)
- **Points it owns:** —
- **MCP tools:** —
- **Files:** `model/` (the interaction and flow types, their defaults and defensive readers, the devices, screens, `DESIGN_PROTOTYPE` and the pruning), `prototype.constants.ts` (the record type, every trigger, action, animation, … as lists, the limits), `prototype.canvas.ts` (its canvas hooks), `ui/` (empty for now).
- **Not yet:** Smart animate (it needs layers drawn separately), Scroll to and scrolling screens (frames clip their content), Change to (needs components and variants), a Present mode for slides (it will reuse this player), comments and sharing a prototype link (web build).

## How it works

- **Screens** (`model/screens.ts`): a screen is a top-level frame of a design page (`isScreen`: `isFrame(el) && el.parentId === null`). `screensOf(doc, page)` lists a page's in layer order; `screenOf(doc, id)` walks a node's parents up to its screen (the node itself when it's one), `null` when it's on none.
- **Interactions** are an optional node field, `interactions: PrototypeInteraction[]` (`model/interaction.types.ts`): a trigger (`click`, `hover`, `press`, `enter`, `leave`, `drag`, `key` with its `key`, `delay` with its `delay`), an action (`navigate`, `overlay` and `swap` with a screen's id in `to`, `back`, `close`, `link` with its `url`), a `transition` (animation, direction, duration, easing) and, on `overlay` and `swap`, an `overlay` (position, close on a click outside, dim). Any node can have them, a screen included. They're read defensively, as the catalog reads `repeatCopy`: `nodeInteractions(el)` keeps the ones `readInteraction` accepts, `[]` when the field is missing or malformed. `readInteraction` refuses (`null`) a value without an id, with an unknown trigger, action or animation, a `navigate`/`overlay`/`swap` without a string `to`, or a `link` whose `url` isn't `http:`/`https:` (`new URL(url).protocol`); it clamps `duration` to 0–5000 ms and `delay` to 0–60000 ms, fills a missing transition with `DEFAULT_TRANSITION` (`dissolve`, `left`, 300 ms, `ease-out`) and a missing overlay with `DEFAULT_OVERLAY` (`center`, closes outside, dims), and drops fields the trigger or action doesn't use (`key` off `key` triggers, `to`, `url` and `overlay` off the actions without them). `newInteraction(to?)` is a new one: a click that navigates. `writeInteractions(doc, nodeId, list)` writes a node's list in one `doc.update` with no checkpoint (the caller makes the undo step); an empty list clears the field (`interactions: null`, `interactionsPatch`).
- **Flows** are records, like the catalog's brochures: a `prototype-flow` element (`PrototypeFlowElement`: `name`, `page`, `start`, `platform`, `device`, `orientation`, `hints`) whose kind (`PrototypeFlowKind`) isn't creatable, isn't boxed, and draws and hits nothing, so it's never on a page's canvas (`PAGE_SCOPES` shows only nodes). `fillDefaults` gives older records `orientation: "portrait"` and `hints: true` (`PROTOTYPE_FLOW_DEFAULTS`).
- **Devices** (`model/devices.ts`): `PROTOTYPE_DEVICES` lists each platform's device ids, the first its default (mobile `iphone-16`, `iphone-se`, `pixel-9`; tablet `ipad-air`, `galaxy-tab`; desktop `window-mac`, `window-windows`, `window-linux`; web `browser-1280`, `browser-1440`, `browser-fit`). `defaultFlowDevice(screen)` is what a new flow plays on: a screen wider than 600 units gets `web`/`browser-1280`, any other `mobile`/`iphone-16`.
- **`DESIGN_PROTOTYPE`** (`DesignPrototype`, `engine.service(DESIGN_PROTOTYPE)`) is the one place that edits flows and interactions, each write one undo step (it checkpoints first, as `DesignBrochures` does): `flows(page)` (in `index` order), `flow(id)`, `addFlow(page, start, name?)` (the screen must be on that page; named `"<screen> flow"` in its creator's language, `flow.defaultName`; its `index` after the last flow's), `updateFlow(id, patch)` (a new `platform` without a `device` gets that platform's first device; an empty name is ignored), `removeFlow(id)`, `interactions(nodeId)`, `setInteractions(nodeId, list)`, `addInteraction(nodeId, ix)`, `removeInteractions(nodeIds)` (every node in one step) and `linksTo(screenId)` (the nodes with an interaction showing it).
- **Deleting** (`prunePrototype`, the module's `onRemove`, in the deletion's undo step): in one pass over the document, a flow whose page or starting screen was deleted goes, and a node that stays drops its interactions whose `to` was deleted (the rest are written back).
- **Copies** need no `prepareCopies` hook: the clipboard's `remapIds` rewrites every element id in a copy, so a link to a screen copied with it points at the screen's copy, and a link to a screen that wasn't copied keeps pointing at the original. Flows aren't copied with their screens.

# Canvas document

_How it works. The rules are in the root [CLAUDE.md](../../../CLAUDE.md)._

## Content lives only in the Yjs doc

- **Content lives only in the Yjs doc.** Each element is a `Y.Map` inside the `"shapes"` map (the name is kept so existing files load). Order is a fractional-index string (`index`), and lexicographic order is z-order.
  - All edits go through `CanvasDocument` methods (`add`, `update`, `updateMany`, `remove`), which transact with `LOCAL_ORIGIN` so `Y.UndoManager` tracks only local changes.
  - Call `doc.checkpoint()` before a user action to start a new undo step.
  - **After-edit hook:** the product's `afterEdit(doc, change)` (point `afterEdit`: every module's hook, in module order; `doc.setAfterEdit`, set by the engine) runs when the outermost edit ends, inside its transaction and so its undo step, with an `EditedChange` (`updated` ids, `removed` elements, `before`: the changed fields' earlier values, `tokens`: the token records written, `meta`: the title or description changed); its own writes run it again with what they changed, until nothing does (at most 32 passes; `update` only records fields whose value changes). Untracked updates run it too; `addUntracked`/`addAllUntracked` (what a file opens with, imports) don't, and undo/redo don't. `doc.deferAfterEdit()` holds it back until the returned function is called (the select tool's drags, so moved elements aren't put back mid-drag; it runs once after `onMoved`, and the drag holds its checkpoints, `holdCheckpoints`, from its start until then, so the hook's writes are in the drag's undo step however long the pointer rested). `doc.ids()` and `doc.field(id, key)` read the store without reading whole elements.
  - Binary data (image files) lives in the doc's `"assets"` map (`doc.addAsset`, `doc.getAsset`), keyed by a `createId()` id that elements point at. It's outside the undo history and shared by copies of an element. `doc.assetIds()` lists them and `doc.removeAssets(ids)` deletes some (not an undo step either), only for assets nothing points at any more: the design's data module drops old data snapshots when the file is saved (`pruneSnapshots`); nothing else deletes unused assets yet. Kinds name the assets an element shows with `kind.assets(el)`. The renderer decodes each one into textures as sharp as it shows (`render/image-cache.ts`, see Render cost; SVGs are rasterized at the level's size, `render/svg-image.ts`), and a drawer shows it with `view.placeImage(assetId, box, fit?)` (proportions kept: `contain`, the default, or `cover`, which crops). SVG icons are drawn with `view.placeIcon(key, svg, box)`, parsed once per icon.
  - The file's own pictures are described by `LibraryAsset` records in its `"assetIndex"` map (`doc.assetIndex()`, `setAssetIndexEntry`, `removeAssetIndexEntry`, `observeAssetIndex`), the bytes staying in `"assets"` under the same id; like `addAsset`, neither is an undo step (the Assets tab, `canvas/libraries/local-assets.ts`). `LibraryAsset` is declared here (`library-asset.types.ts`) and re-exported by `canvas/libraries`; `isLibraryAsset(value)` checks a stored record, for files and libraries alike.
  - The document's own **title and description** live in its `"meta"` map (`doc.meta()`, `doc.setMeta(patch)`, `doc.observeMeta`; undoable like elements). The title is shown instead of the file name when set (`displayName(file)` in `shared/core`); `useDocumentMeta(doc)` (`canvas-ui`) reads it in React. `doc.onChange(listener)` fires on any change (elements, view state, assets, meta): it's what dirty tracking and autosave listen to.
  - **Who changed the tokens:** `doc.observeTokens((ids, source) => …)` fires once per transaction that changed token records, with a `TokenChangeSource`: `local` (made here by the user, an agent or undo/redo: `transaction.local` and not `UI_ORIGIN`, so untracked writes such as a library mirror or a migration aren't), `remote` (applied from another peer, a live session's guest or host) and `previous` (each changed record's value before the transaction, `undefined` for one added). Project libraries use it to send the user's edits to the libraries, undo and redo included, which the after-edit hook never sees (see [libraries/](../libraries/README.md)).
  - The **project link** lives in the `"project"` map (`doc.projectLink()`, `doc.setProjectLink(link)`, `doc.observeProjectLink`): a `ProjectLink` (`projectId`, `libraryIds`: the libraries the file uses by id, or `"all"`) tying the file to a project (`null`: a loose file). It's part of `encode()` and so of the file, and not an undo step unless written with `setProjectLink(link, { undoable: true })` (`ProjectLinkOptions`: as the current actor, joining the step being recorded; the map is in every history's scope for that, while the default writes are untracked).
  - A document reads elements through the product's kinds (`new CanvasDocument(kinds)`, `CanvasDocument.fromUpdate(kinds, bytes)`): `doc.get`/`doc.all` return only registered types, with `kind.fillDefaults` applied. Elements of unregistered types (e.g. DB or ER shapes in older boards) stay in the doc untouched but aren't shown; `doc.unregistered()` says where they sit (`UnregisteredElement`: id, type, index, box), for a stand-in such as the HTML export's placeholder. Reads are cached per element (dropped when it changes: the document's own writes, and `beforeObserverCalls` for undo, redo and remote updates), so a change to a few elements doesn't read the whole file again; `doc.all()` is a new array of **shared elements: never mutate one** (they're frozen in development builds).

## Actor documents

- **Actor documents** (`canvas/document/`): `doc.runAs({ origin, placement }, fn)` makes the synchronous edits inside `fn` with another transaction origin and placement (calls nest), `doc.createHistory(origin)` is a `DocumentHistory` (a `Y.UndoManager` tracking only that origin; steps carry labels, `setNextLabel`, kept across undo and redo; `onChange` reports `added`/`undone`/`redone`/`cleared`), and `actorDocument(doc, { actor, history })` is a `Proxy` whose writes run as the actor and whose undo methods are its history's, typed `CanvasDocument` so tools, services and `asUndoStep` don't change. The user's own history is `doc.history` (`LOCAL_ORIGIN`).

## Read-only

- **Read-only:** `CanvasDocument.setReadOnly(true)` makes every local edit (elements, assets, meta, undo/redo) a no-op, tools, panels and agents alike; a viewer's editor has it and no toolbar.

## Forks

- **Forks:** `doc.settled()` is false when the last outermost edit's after-edit passes ran out (32) with changes left, which are dropped: harmless while editing, but `exportCopy` throws then, so an export never prints a half-made copy. `doc.fork()` is a throwaway copy of the document as it is now, for work the user's file must never see (the brochure export's repeated pages and card copies): a new Y.Doc built from `encode()`, no undo history (its histories, the user's and any actor's, keep no steps: `DocumentHistory`'s `record` off), no after-edit hook or placement until they're set, writable even when the original is read-only, and `destroy()` destroys its Y.Doc too. `engine.scratchWorkspace(fork)` sets the product's `afterEdit` on it (so syncs run on its edits) and gives a headless `ActorWorkspace` over it, as agents' are; `engine.dropScratchWorkspace(workspace)` destroys it and takes the hook off (the engine does it for every one when it's destroyed, and their exports fail from then on); `workspace.exportCopy()` (any workspace: the engine or a collaborator's) wraps both with a `dispose()` and lets the product ready the fork first (`CanvasProduct.exportCopy`, see [workspace/](../workspace/README.md)).
  - **Assets are copied, not shared:** the fork holds its own `"assets"` map, so an asset written to it (`addAsset`) never reaches the original or its file. A scratch workspace's exports read pictures from the fork (`SnapshotOptions.readAsset`); the canvas's image cache never takes its bytes and is borrowed only for pictures it holds already (same id, same file). Copying the bytes costs memory while it lives; dispose of it as soon as the work is done.
  - **What a fork must not do:** be saved or encoded to a file, be handed to a live session (provider, awareness, `doc.onChange` listeners for autosave or dirty tracking), or outlive the work it was made for. State kept per Y.Doc in memory (the data module's `SharedState`: its editor context, Updates and data phase) starts afresh on it, so it has no editor context (data sources can't be Updated on it, and removing one there deletes no device secrets) and its data phase is its own.
